{{- /* 404.html — version-aware "page not found". WHY THIS EXISTS. Hextra ships a 404 that says "This page could not be found." and nothing else. On a VERSIONED docs site that is the least useful answer available, because the overwhelmingly common way to reach a 404 here is a stale link into a version tree — either a retired version that is no longer built (agentgateway 2.1.x/2.2.x are archived as .zip in the hub, so every URL under them 404s), or a live version where the topic has since moved. In both cases the page the reader wants usually still exists, one version segment away, and we can find it for them. Reported as solo-io Slack: "can we setup a redirect so that old version urls go to latest instead of 404", e.g. /agentgateway/2.1.x/install/ui/setup/ → /agentgateway/latest/install/ui/setup/. THIS IS THE SECOND LAYER, NOT THE FIRST. A retired version should be caught by a path-preserving 301 in the consumer's hosting config (firebase.json in solo-io/docs), which is cheaper, keeps the SEO signal, and costs no round trip. This template handles what a blanket redirect CANNOT: the topic that does not exist at the same path in the destination version. Do not read the presence of this file as a reason to skip the redirect rules. WHY IT IS STANDALONE (no navbar, no sidebar, no baseof). A 404 has no real page context: it is emitted once per build and served for arbitrary paths, so `.RelPermalink` is "/404.html" for every request it answers. Every chrome partial in this theme (sidebar.html, version-banner.html, breadcrumb.html) resolves its state through utils/version-root.html against that RelPermalink, so on this page they would all render the "not versioned" branch — a navbar and sidebar for nowhere. Rendering them is also seven products × two brands of build risk for chrome nobody reads. Hextra's own 404 is standalone for the same reason; this keeps that shape and spends the page on the one thing a 404 can usefully do. WHAT IT DOES NOT DO. It never auto-redirects. The reader is already at a broken URL and an automatic bounce would hide that fact, strand them somewhere they did not ask for, and (when the guess is wrong) look like the site is malfunctioning. Every destination is offered as a link. DARK MODE uses `prefers-color-scheme` only, not Hextra's `.dark` class. The class is set by Hextra's theme script, which is loaded from baseof.html — absent here by design. A reader whose site preference disagrees with their OS preference sees the OS one on this page alone. That is the accepted cost of staying standalone. */ -}} {{- /* Version data for the client. Hugo knows three things the browser cannot: which version is `latest`, which version segments are legitimate, and where this site's root is. Everything else is derived at runtime from location.pathname, because that is the only place the REQUESTED path exists — Hugo built this file without knowing it. Product filtering matters. site.Params.versions may list OTHER products' versions (hugo-gateway.toml carries Gloo Edge's 1.19.x–1.22.x alongside Gloo Gateway's, and hugo-gloo-mesh-enterprise.toml carries Solo Istio's), so an unfiltered list would let /gateway/1.21.x/ resolve against Edge's entry. Prefer entries belonging to site.Params.currentProduct, exactly as utils/match-version-entry.html does; fall back to the whole list on a site that sets no currentProduct (agentgateway-oss-website and kgateway-oss both omit it). */ -}} {{- $curProd := site.Params.currentProduct | default "" -}} {{- $ownVersions := slice -}} {{- range site.Params.versions -}} {{- if or (eq $curProd "") (eq (.product | default "") $curProd) -}} {{- $ownVersions = $ownVersions | append . -}} {{- end -}} {{- end -}} {{- if not $ownVersions -}}{{- $ownVersions = site.Params.versions | default slice -}}{{- end -}} {{- /* RETIRED VERSIONS STAY IN THIS LIST ON PURPOSE. agentgateway keeps 2.1.x and 2.2.x in params.versions (hidden from the dropdown via a blank `dropdown`) after archiving their content. Including them here is what lets the client RECOGNIZE /agentgateway/2.1.x/… as a version segment rather than a content path. This list answers "is this segment a version?", never "does this version still build" — the HEAD probes answer that, and they are authoritative because they ask the server. */ -}} {{- $known := slice -}} {{- range $ownVersions -}} {{- with .linkVersion -}}{{- $known = $known | append . -}}{{- end -}} {{- end -}} {{- /* The destination version. `latest` when the site declares one, else the first configured entry — a site with no `latest` entry (some OSS sites ship only numbered trees) still gets a usable target instead of "". */ -}} {{- $latest := "" -}} {{- range $ownVersions -}} {{- if and (eq $latest "") (eq (.linkVersion | default "") "latest") -}} {{- $latest = .linkVersion -}} {{- end -}} {{- end -}} {{- if eq $latest "" -}} {{- range first 1 $ownVersions -}}{{- $latest = .linkVersion | default "" -}}{{- end -}} {{- end -}} {{- $cfg := dict "home" site.Home.RelPermalink "latest" $latest "versions" $known "productName" (site.Params.product | default site.Title | default "the documentation") -}} {{- /* TRANSLATION. Every reader-facing string on this page resolves through i18n with the English literal as its fallback, the same shape version-banner.html uses for `bannerID`. A consumer that ships no i18n table — which is every OSS site — gets the literals and is unaffected; the docs hub, which publishes content/ja/, can translate the page. Verified that a MISSING key is silent: Hugo returns "" and logs no warning for it, so this does not add a WARN to consumers that fail CI on unallowlisted warnings. (Checked against the fixture build before this was extended past the first string.) Keys are prefixed `not_found_` in the i18n table; the short names below are local.
