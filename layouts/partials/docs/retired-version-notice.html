{{- /* retired-version-notice.html — tell a reader that the version they asked for is gone, after a hosting-level redirect has already moved them. WHY THIS EXISTS. A retired version is caught by a path-preserving 301 in the consumer's hosting config, which is the right mechanism: one hop, no interstitial, SEO signal preserved. But it is SILENT. The reader clicks a link to 2.1.x, the address bar says something else, and nothing on the page accounts for the difference. That was tolerable when only the version segment changed. It stopped being tolerable when agentgateway moved its version trees under a section segment, because a reader is now relocated on two axes at once — /agentgateway/2.1.x/install/… becomes /agentgateway/kubernetes/latest/install/… — and the destination URL shares almost nothing with the one they clicked. HOW THE CONTEXT SURVIVES THE REDIRECT. It cannot be recovered client-side: by the time this page loads, the requested URL IS the destination URL, and the version the reader actually asked for is gone from every source the browser can see (`document.referrer` is empty on a 301 from a bookmark, and wrong when the link came from a search engine). So the hosting rule hands it forward explicitly: "source": "/agentgateway/2.1.x/:path*" "destination": "/agentgateway/kubernetes/latest/:path*?fromversion=2.1.x" Firebase merges that with any query string the reader already had (`?fromversion=2.1.x&foo=bar`), so the parameter is additive, not destructive. WHY THE URL IS CLEANED UP AFTERWARDS. The parameter has done its job the moment this renders. Leaving it in the address bar means every copied or shared link carries it, and every one is a distinct URL to a crawler for the same page. `history.replaceState` drops it without a navigation, so the URL the reader copies is the canonical one. This runs whether or not the notice renders, so an unrecognized value still gets tidied. WHY IT IS NOT DISMISSIBLE-WITH-MEMORY. No localStorage, no cookie. The notice is tied to one arrival from one stale link, not to a site-wide state the reader should be able to mute — and a reader who follows a second stale link a week later needs telling again. RENDERED next to `version-banner.html` in docs/single.html and docs/list.html rather than in the `docs/chrome-top.html` slot, because both OSS consumers override that slot and would silently lose this. */ -}} {{- $vr := partial "utils/version-root.html" . -}} {{- /* The version this page actually belongs to, for the "you are here now" half of the sentence. Falls back to the configured latest when the page is not in a recognized version tree, which is the case for a product landing page that a bare // rule points at. */ -}} {{- $current := $vr.currentVersion | default "" -}} {{- if eq $current "" -}} {{- range site.Params.versions -}} {{- if and (eq $current "") (eq (.linkVersion | default "") "latest") -}} {{- $current = .linkVersion -}} {{- end -}} {{- end -}} {{- end -}} {{- /* The set of version segments this site considers legitimate. The notice renders ONLY for a value in this list: `fromversion` arrives in a URL, so it is reader-controlled, and echoing an arbitrary string back into the page is how you turn a helpful banner into a content-injection vector. An allowlist makes that impossible by construction — the value is used to SELECT a known string, never to produce one. Retired versions are still present in params.versions (hidden from the picker with a blank `dropdown`), which is exactly what makes them matchable here. */ -}} {{- $curProd := site.Params.currentProduct | default "" -}} {{- $known := slice -}} {{- range site.Params.versions -}} {{- if or (eq $curProd "") (eq (.product | default "") $curProd) -}} {{- with .linkVersion -}}{{- $known = $known | append . -}}{{- end -}} {{- end -}} {{- end -}}
