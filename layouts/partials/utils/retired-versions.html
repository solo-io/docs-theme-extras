{{- /* retired-versions.html — the set of version segments this site used to publish and no longer does. Returns a slice of strings; empty on a site that has retired nothing. WHY THIS IS NOT JUST `params.versions`. docs/retired-version-notice.html and 404.html both need to recognize a `?fromversion=` value handed forward by a hosting-level redirect. Until this partial existed they answered that question from `params.versions`, which meant a retired version's entry had to STAY in the table long after its content tree was archived — an entry that renders nothing, is hidden from the picker with a whitespace `dropdown`, and exists purely to be matched against. That is an invisible obligation, and it was broken in practice: solo-io/docs 94be4fc64 added the agentgateway 2.1.x/2.2.x redirect rules and deleted those two entries in the same commit, which left the redirect working and the explanation silently gone. Nothing failed. So the question is asked of the hosting config instead, which is the only place that actually knows: a version is retired exactly when something is redirecting away from it. The rule that causes the move is now the rule that explains it, and the two cannot drift. THREE SOURCES, unioned. A consumer opts in by doing nothing. 1. `params.retiredVersions` — an explicit list, for a consumer whose redirects live somewhere this partial cannot read (an edge worker, an ingress rule) or who wants to name a version the hosting config does not. 2. `static/_redirects` — the Cloudflare Pages / Netlify format, used by agentgateway-oss-website and kgateway-oss. One rule per line, whitespace separated, destination second: /docs/1.0.x/* /docs/latest/:splat?fromversion=1.0.x 301 3. `firebase.json` — the docs hub. Every hosting target's `redirects` array is walked and each `destination` read the same way. IN ALL THREE CASES a rule contributes nothing unless it carries `fromversion=`. That is deliberate: a redirect exists for plenty of reasons that are not a retirement (a renamed page, a moved section), and only the ones that opted in by appending the parameter are claiming "the version this reader asked for is gone". Retiring a version is therefore one edit, in the hosting config, and the notice follows. WHERE IN THE RULE THE PARAMETER IS READ differs between the two file formats, and only one of them is exact. The firebase.json branch passes `.destination` and nothing else, so a source pattern cannot contribute. The `_redirects` branch passes the WHOLE LINE — source, destination and status code — and utils/retired-version-param.html takes the tail of the first `fromversion=` it finds anywhere in it. In practice that is the destination, because a Cloudflare/Netlify source is a path pattern and the format has no way to match on a query string, so the parameter can only appear on the right-hand side. It is not a guarantee, though, and a line that somehow carried the marker on the left would be read from there. Splitting the line on whitespace and taking field 2 would close it; that was not done because the terminators in retired-version-param.html already handle an unsplit line and a second parse of the same string is a second place for the two formats to disagree. NOT FILTERED BY PRODUCT, on purpose, and it matters most for the hub, where one firebase.json carries every product's rules.
