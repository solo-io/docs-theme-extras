This file used to be 211 lines: six shape heuristics choosing between four emit strategies, because Hugo does not expose whether a shortcode was called in percent or angle form and the template was guessing. It is now condition resolution plus one emit site. Every one of those strategies existed to undo damage caused by the others — the trailing-step and table-row paths raw-emitted to escape RenderString, the $isFullTable path rendered to escape raw emit, and the fenced-block path raw-emitted to escape a double render. Emitting `.Inner` untouched removes the reason all four existed. See utils/gate-emit.html for the verification behind that, and utils/gate-decide.html for the shared condition evaluator. TWO TOKENS, NOT ONE — the build condition AND the section segment. `page-context` resolves ONE condition, and in "siteParams" mode (the multi-product hub, solo-io/docs) that condition is the site-wide `Site.Params.buildCondition`: a PRODUCT id — `agentgateway`, `envoy`, `gme`, `gmg`, `gg`. It cannot vary within a build. A product that ships parallel documentation sections (see utils/section-segment.html) needs a SECOND axis. agentgateway enterprise has `kubernetes` and `standalone` sections; with only the product token, every `include-if="kubernetes"` / `include-if="standalone"` gate in content shared with the OSS site was dropped on BOTH sections — not gated, dropped. This reuses that contract rather than adding a parallel one: a gate fires if EITHER the product condition or the section segment is named. WHY THE SEGMENT IS ADDITIVE ONLY, never a token on its own. The outer `ne $condition ""` guard is deliberately kept, so a page with no build condition still emits nothing even when a section segment resolves. That keeps the change strictly additive: no page that previously emitted nothing starts emitting because of a segment alone.
